測って捨てながら作る

SoundSpace の設計と開発ワークフロー。Macを持たずにiPhoneアプリを作り、App Storeの審査を3回落ちて公開するまでの記録です。

2026年9月10日 · サポートへ戻る

音のアプリを作っていて一番多かった作業は、実装ではなく「作ったものを測って捨てる」ことでした。良さそうに思えた案が、測ってみると成立していない。この記事はその記録です。

前提: 今回作ったもの

SoundSpace は、40Hzの聴覚刺激と瞑想音楽を、意図的に混ぜずに提供するiPhoneアプリです。iOSネイティブのアプリですが、画面はWKWebViewに静的HTMLを載せた構成で、音の再生と課金だけをSwiftが担います。

サーバーはありません。BGM 20曲と環境音7層、合わせて92MBの音源をすべてアプリに同梱しているので、機内モードでも全機能が動きます。通信を必要とする箇所が一つもないため、アカウント登録もありません。

この技術構成を選んだ理由

もともとPWA（ブラウザで動くWebアプリ）として作っていました。ネイティブ化した理由は2つです。

1つ目はiOSのPWAは画面ロックで音が止まることです。瞑想や作業中の利用を想定したアプリで、画面を消すと音が消えるのは致命的でした。ネイティブなら UIBackgroundModes: audio が使えます。

2つ目は課金です。StoreKit 2 は端末内で購入を検証できるので、サーバーを持たずに課金が成立します。Transaction.currentEntitlements と Transaction.updates を購読しておけば、解約・返金・家族共有のように購入操作を経ずに権利が変わった場合も反映されます。「バックエンドを持たない」という前提を壊さずに有料機能を作れました。

画面をWebViewのままにしたのは、音の生成と解析のロジックがすでにJavaScriptで書けていて、それをSwiftへ移植すると実測で担保している値を作り直すことになると判断したからです。生成はJS、再生はネイティブ、と役割を分けました。

解決したい課題

「40Hz」を掲げた音源はすでに大量にあります。しかしその多くがバイノーラルビートという方式です。左右の耳にわずかに違う周波数を流し、その差をうなりとして知覚させる方式です。

ここに問題があります。左右の周波数差は30Hzを超えると、うなりとして知覚されにくくなります。つまり40Hzでは方式として成立しにくい。40Hzの聴覚刺激を扱う研究で一貫して使われてきたのは、音そのものを毎秒40回強弱させる振幅変調（アイソクロニック）です。

そして利用者には、手元の音源がどちらの方式なのか、本当に主張どおりの刺激を含んでいるのかを確かめる手段がありません。ここを埋めるのがこのアプリの出発点でした。

この構成で一番重要なのは、Gamma を音楽から独立したタブに置いたことです。理由は次の節にあります。

測って捨てた選択肢

ここがこのアプリの設計の中心です。良さそうに見えて成立しなかった案を、順に記録します。

音楽に40Hzの変調を掛ける

最初に試した案です。瞑想BGMそのものを毎秒40回強弱させれば、音楽と刺激が一体になるはずでした。

結果はザラつきでした。40Hzは聴覚の粗さ帯域（およそ15〜300Hz）に入るため、この速さで音量を上下させると、どんな音でも必ずガサガサした質感が出ます。パラメータを変えても回避できません。研究が音楽ではなく単純な音やクリックを使ってきたのは、おそらくこの理由です。

変調していない音楽を、刺激の横に並べる

次に、刺激は刺激として鳴らし、音楽は加工せず横に置く案を試しました。これも却下です。

2つの理由がありました。1つは聴感で、脈打つ音が音楽の中の異物として残ること。もう1つは測定で分かったことです。

変調していない音を隣に置くと、変調の谷が埋まります。音楽を70%の音量で混ぜたところ、実効的な変調深度は100%から26%まで落ち、アプリ自身の検出器ですら40Hzを検出できなくなりました。刺激として数えたい音は、すべて変調段を通す必要がある——これは測って初めて分かったことです。

この2つを捨てた結果、「刺激と音楽は混ぜない。経路ごと分ける」という現在の設計になりました。

強度プリセットを持たせる

「やさしい・標準・はっきり」の3段階を用意していました。これも削除しました。

採用した音源が完全に断続する波形（深度100%）だったため、そこから浅い変調を作ることができません。選べないものを選べるように見せることになるので、操作そのものを消しました。現在変えられるのは再生時間と全体音量だけです。

測って決めたこと

同梱しているGamma 40の音源は、次の値で固定されています。すべて実測値です。

指標実測値
変調周波数39.999 Hz
変調深度100.0%
ループ長177.754444 秒（7,110周期）
ピーク0.9624
継ぎ目の段差0.003510（隣接サンプル差の78.2%点）

ループ長が中途半端な小数なのは、変調周期の整数倍に合わせているからです。39.999Hzで7,110周期。ここがずれると、ループの折り返しで位相が飛びます。

ループの継ぎ目で鳴るクリック音

環境音でつまずいた話です。クリスタルボウルの音源が、57秒ごとに小さく「チッ」と鳴りました。

ループの作り方自体は正しく、符号化前のPCMは問題ありません。壊していたのはAAC符号化でした。ファイルの両端に、ランプ状の再構成誤差が出ていました。先頭の実測誤差はピークの17%に達していました。

効かなかった対策を先に書きます。ビットレートを上げても（96k→320k）、クロスフェードを伸ばしても（3秒→20秒）、末尾のパディングを切り詰めても、継ぎ目の順位は最悪のまま変わりませんでした。

効いたのは、符号化する前に両端を5ミリ秒で無音へ落とすことでした。それだけで段差が0.079から0.00068へ、順位が100%点から9.1%点へ改善しました。全層に適用した結果です。

層処理前処理後
シンギングボウル100.00%9.11%
波87.60%5.41%
焚き火95.83%31.87%

なお20ミリ秒以上にすると継ぎ目に谷ができるので、伸ばしてはいけません。

素材の良し悪しは、スペクトルだけでは決まらない

環境音は合成をやめ、すべて実録のCC0素材に置き換えました。合成版は「それっぽい何か」で止まり、粒の密度や遠近が再現できないと判断したためです。

そのうえで、森の素材を1つ不採用にしました。158秒を10秒刻みで走査したところ、2〜8kHzの成分が最大1.47%しかなく、スペクトル重心も最高226Hzでした。葉擦れの音なら2〜8kHzが数十%を占め、重心は2,000Hzを超えます。入っていたのは低い唸りだけで、どこを切り出しても葉になりませんでした。

逆に、雨と川が聞き分けられないという問題は、スペクトルでは説明できませんでした。重心は2,070Hzと1,915Hzでほぼ同じです。差が出たのは時間構造で、雨の包絡線の変動係数は0.24（全音源で最も定常）、粒の検出は毎秒0.0回でした。粒立ちのない雨は、信号としては川と同じです。以降、素材はスペクトルと時間構造の両方で判定しています。

CHECKタブ — 鳴らすのではなく測る

手元の音声ファイル（mp3 / m4a / wav）を渡すと、変調周波数、変調深度、ピーク明瞭度、左右の周波数差、照合した帯域を数値で返します。左右差を見るので、アイソクロニックとバイノーラルの方式の判別もできます。

この機能は、素朴な実装を3つ捨てたうえで成立しています。

捨てた実装何が起きたか
モノラルに合成してから解析するバイノーラル素材が「アイソクロニック」と誤判定される。左197Hzと右203Hzを足すと、和の中に本物の6Hzのうなりが生じるため。左右を別に解析する
全帯域で1つの包絡線スペクトルを取る2つの倍音どうしのうなりを、意図的な変調と誤判定する。136.1Hzと181.5Hzが「強い45.4Hzの刺激」に見える。帯域を分け、全帯域に存在することを要求する
1次フィルタの縦続で帯域を分け、幾何平均で束ねる漏れが大きすぎ、かつ1帯域にしかない成分を通してしまう。FFTのビンをゼロ化した解析信号を使い、帯域はビンごとの最小値で結合する

検出の限界も測って決め、画面に書いてあります。深度20%以上は確実に検出、10%前後は音楽自体のうねりと区別がつききらないため「弱い」と表示、5%以下は検出できません。

Macを持たずにiPhoneアプリを出す

開発機はWindowsです。iOSアプリはXcodeでしかビルドできず、XcodeはmacOSでしか動きません。この制約をどう回避したかが、開発フローの中心になりました。

この構成には費用の落とし穴がありました。GitHub は macOS の実行時間を Linux の10倍で数えます。privateリポジトリの無料枠は月2,000分ですが、macOSだと6分のジョブで60分消費されるため、実質30回ほどのビルドで尽きます。

開発が集中した数日で枠を使い切り、審査対応が数日止まりました。原因はソースを変更するたびに自動でビルドが走る設定にしていたことです。現在は手動実行のみに変え、ビルドは「出すとき」だけ回しています。

Xcode Cloud への移行も検討しましたが、.xcodeproj がリポジトリに必要で、この構成ではCIがXcodeGenで毎回生成しているため使えませんでした。

開発ワークフローと役割分担

実装と文章はAI（Claude Code と Codex）に、判断と実機確認は人が担当しました。

担当やったこと
人音の採否を試聴で決める。実機での動作確認と画面収録。課金設定と支払い。公開の最終判断
AI実装。音源の測定と処理。ストア掲載文。審査への返信。CIの整備

この分担で外せなかったのが試聴です。測定値が良い音源が良い音とは限りませんでした。スペクトルも時間構造も基準を満たした素材が、聴くと「それっぽい何か」で止まっていたことが何度もありました。音楽の採否は測定では決まらないので、人が聴いて確認した記録を残さないと採用しない運用にしています。

もう一つ、AIに任せられなかったのが実機の画面収録です。App Review が要求したのは「実機で撮影した操作の録画」で、これはiPhoneを持っている人にしか作れません。

品質確認のワークフロー

音のアプリで怖いのは「気づかないうちに音が変わっていること」です。次の3つで防いでいます。

確認内容
参照音源との照合CHECKタブが、既知の変調を持つ校正用音源7本に対して7/7で一致すること
同梱音源の回帰39.999Hz / 深度100.0% / 177.754444秒 / ピーク0.9624 / 継ぎ目0.003510 が変わっていないこと
CIでの申告検査ビルドしたIPAの UIDeviceFamily を読み、対応デバイスの申告が意図どおりであること

文言についても通し読みの工程を置いています。効能を示唆する表現がゼロであることの確認です。日本では薬機法と景品表示法に直接かかり、無料で配るのと有料で売るのとでは厳しさが変わります。

App Store 審査の記録

3回落ちました。順に記録します。

1回目 — Guideline 2.1（情報要求）

「審査履歴の浅いデベロッパアカウントからの提出なので、追加情報が必要」という定型の要求でした。内容を否定されたものではありません。

要求は7項目で、目的と対象、機能への導線、使用している外部サービス、地域差、第三者素材の権利、アプリ内購入の内容。そして実機で撮影した画面収録です。この収録が必須で、起動から通常の操作、購入画面までを含める必要がありました。

2回目 — Guideline 3.1.2(c)（サブスクリプションの表示）

これは正当な指摘でした。購入画面が「7日間無料トライアル」と「¥3,600 / 年」を別々の要素として並べていただけで、両者が繋がっていませんでした。条項の段落にも「期間終了の24時間前までに解約しない限り自動更新されます」とはありましたが、トライアルが終わった時点で課金が始まるとは書いていませんでした。

修正は、条件を1つの文にまとめることです。

7日間の無料トライアル終了後、¥3,600 / 年が自動で請求されます

あわせて、文言を焼き込むのをやめました。StoreKit が返す値——導入オファーの期間、支払い方式、そしてその利用者がオファーの対象かどうか——から組み立てるようにしています。対象でない利用者にはトライアルの一文を出しません。受け取れないものを宣伝する状態が、構造的に起きない作りにしました。

3回目 — 承認

4項目（アプリ本体、サブスクリプショングループ、月額、年額）すべてが承認されました。

なお、公開前に最も心配していたのは Guideline 4.3(b)、いわゆる市場の飽和による却下でした。条文は sound effects や simple timers を名指ししており、当初の掲載文は「環境音を重ねて時間を計るアプリ」に読める書き方でした。1行目を「40Hzの聴覚刺激と瞑想音楽を、意図的に混ぜずに提供するアプリです」に書き換えましたが、結果として4.3は一度も指摘されませんでした。

プライバシーと安全性の前提

  • アカウント登録・ログインがありません
  • 実行時に外部サービスへ接続しません。データ提供者、認証、解析、広告、トラッキングのいずれも使っていません
  • 音源はすべて同梱で、実行時に取得しません。機内モードで全機能が動きます
  • 記録は端末内にのみ保存されます
  • 音声処理と解析はすべて端末上で行われます。渡したファイルが送信されることはありません
  • 環境音はすべてCC0素材で、出典URL・作者・ライセンス・原音のハッシュを記録し、アプリ内にも出典を表示しています
  • 医療機器ではありません。診断・治療・予防・効果測定を目的としません
  • 効果の測定機能は実装していません。スマートフォンで測れるのは反応時間などの行動指標で、脳波ではありません

最後の項目について補足します。行動指標は日内変動が大きく、数十回の試行で出た差は練習効果か偶然です。測れないものを測れるように見せることはしないという方針で、機能そのものを作りませんでした。

まとめ

このアプリで一番時間を使ったのは、実装ではなく測定と、その結果を受けて案を捨てることでした。

音楽に40Hzを掛ける案、刺激の横に音楽を並べる案、強度を3段階にする案、合成で環境音を作る案、ビットレートを上げてクリック音を消す案。どれも作ってから捨てています。捨てた判断はすべて、聴感か測定値のどちらか、あるいは両方に基づいています。

AIは実装、測定、文章、審査対応をかなり速くできます。しかし「この音を使うかどうか」は、人が聴いて決めるしかありませんでした。測定値が基準を満たした素材が、聴くと使えないことが何度もありました。逆に、聴いて良いと思った音が測ると成立していないこともありました。両方を突き合わせる作業が、結局このアプリの中身になっています。
